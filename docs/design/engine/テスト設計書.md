# テスト設計書：ビルド環境における品質担保方針

## 1. 目的
本プロジェクトでは「ビルドコマンド（npm run build 等）の実行を禁止」し、コードロジックと設計による検証を原則とする。本ドキュメントは、この制限下でプロジェクトの整合性と品質を担保するためのテスト手法を定義する。

## 2. 検証の役割分担
- **開発者（Hermes Agent）**:
  - 実装ロジックの静的解析および単体テストのコード化。
  - プロジェクト構成および構造欠損の検知用スクリプトの作成。
- **管理者（ぷりんさん）**:
  - 実際のプレイ体験（プレイ感）の確認。
  - 必要に応じて Agent が提供した CLI ツールやテストスクリプトの手元実行による状態確認。

## 3. 検証手法とコマンド定義
本プロジェクトにおける検証は以下の通りとする。

### A. 構造チェック (`npm run test`)
- **目的**: プロジェクトの構成（設計書、設定ファイルの欠損）の検知。
- **実行内容**: `test-design.js` によるファイル存在チェック。
- **基準**: 設計書一式が `docs/design/` 配下に揃っていること。

### B. ロジック検証 (Agent による静的解析)
- **目的**: 合成ロジック、再創世（プレステージ）処理の正当性確保。
- **手法**: コードの読み込みによる静的解析およびロジックのトレース。
- **基準**: 設計書の計算式とソースコード（`src/engine.ts` 等）の一致。

### C. 動作検証 (手元実行)
- **目的**: 複雑な結合動作やプレイ感の検証。
- **手法**: 提供された CLI スクリプトの実行。
- **制限**: API制限（RPM/TPM/RPD）を遵守し、コンテキスト消費を最小限に抑えるため、大量のループ処理等は避けること。

## 4. レートリミット対策
- 大量のコンテキストを消費するような大規模テストスイートの実行は禁止とする。
- 検証は常に小さな単位（単一関数、単一ファイル）で行い、Agentの推論コストを最小化する。
