# 設計の進め方と管理ルール

本プロジェクトでは、上流から下流へ順に設計を詳細化し、上位設計の変更が下位設計に波及する「トレーサビリティ」を確保します。

## 1. 設計書階層構造
最上流から最下流へ、以下の順序で定義します。

| 階層 | ファイル名 | 内容 | 役割 |
| :--- | :--- | :--- | :--- |
| **1. 最上流** | `00_概念設計書.md` | コンセプト、体験、ターゲット | ゲームの「魂」を定義 |
| **2. 中流** | `01_基本設計書.md` | コアサイクル、目標、UI方針 | 機能の全体像を定義 |
| **3. 下流** | `02_システム設計書.md` | 計算ロジック、データ構造 | システムの「骨格」を定義 |
| **4. 最下流** | `03_詳細設計書.md` | インターフェース、実装手順 | 実装の「ガイド」を定義 |
| **補足** | `テスト設計書.md` | テスト方針・ケース | 機能検証・品質保証 |
| **補足** | `design-doc.md` | 設計検討メモ・議論 | 仕様決定の経緯・補足 |
| **補足** | `dev-roadmap.md` | ロードマップ | マイルストーン・進捗管理 |

## 2. 変更管理ルール
- **上位優先の原則**: 概念・基本設計に変更が生じた場合、必ず中・下流設計書を見直し、不整合を解消すること。
- **紐付け**: 各下流設計書の冒頭には、参照している上位設計書へのリンクを記載する。
- **同期**: 上位の定義値（定数やルール）を変更した際は、下流の具体値もそれに合わせて更新する。

## 3. 実装者の遵守事項
- 実装時に不明点がある場合、勝手に推測せず、設計書の不足として指摘し、まず設計書を更新してからコードを書くこと。
- 「設計書に書かれていないことは実装しない」を鉄則とする。
